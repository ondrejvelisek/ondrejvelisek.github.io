Cost of Abstraction for AI Agents

August 2, 2026 · 16 min read

Over my career I saw many mid-level developers craving more and more abstraction. I was one of them. But over time I see that more is not always better. A truly senior dev abstracts only when it is needed. I believe it is less than most developers think. Therefore AI overuses abstraction too. And you pay up to 30 % more on you total AI agents bill for that.

Over-abstraction is not a new idea but a well-known topic. I got inspired by Dan Abramov's The WET Codebase. Sandi Metz in the post The Wrong Abstraction put it even shorter: "duplication is far cheaper than the wrong abstraction". I want to add my own frontend dev view, my experience with TypeScript, examples I saw over time and find out how agents behave and how much this anti pattern increases our AI costs.


What is abstraction?​

It is a boundary between two parts of code: the code it hides, and the code that uses it via an interface. This interface has a name, is reusable, and can have some parameters. The best example is a function.

function sort(array: Array<number>) {
    // implementation code it hides behind the interface
}
// some higher level code uses the interface
sort([2, 1, 3]);

But there are some other forms of abstraction which may not be that obvious.

  • variable/constant
  • JS class
  • CSS class
  • component
  • file
  • package
  • repository
  • programming language

Try to think about how the boundary is represented in each of those. What its interface looks like. What its name is. What it hides and how to reuse it.


Why abstract?​

Abstractions are crucial for code maintainability. And it's the reason why we are capable of building large systems. Imagine you had to always write code for sorting an array or multiplication of two numbers. Nightmare.

So we abstract to:

  • Hide complexity
  • Name a piece of code
  • Reuse a piece of code

If none of the above is needed, we should not abstract. And even though some of the above applies, we still should consider not to. We need to balance the cost with the benefit.

The question I asked myself is why developers overuse them so often. I see three reasons.

  1. It is a very quiet enemy. It adds up slowly. One wrong abstraction costs almost nothing to us and our velocity. So it's hard to focus on and spot it.

  2. When a developer is afraid of touching the abstraction layer, he rather create a new one. It can be due to a time pressure. So he cant properly read and understand all the logic and adjust the existing layer. Instead, he creates a new one on top of it.

  3. Every junior developer, including me, when starting to code, naturally did not create abstractions much. We focused on the goal. To make it work. It was hard enough and challenging on its own. And we did not have the capacity or time to think about something like abstractions. Junior devs tend to create long functions and files, duplicate code, and do not name the interfaces nicely. And their senior mentors tell them to split the code. Reuse lines. Name the functions better. Hide the complexity behind interfaces, ... Abstract more. It is taught in courses and university lectures. DRY, SOLID, Single responsibility, KISS, one page function, High Cohesion & Low Coupling, Separation of Concerns, ... All those principles are very well known. Because everybody was a junior once. It almost becomes a SW dev culture. Abstractions are perceived as a good code practice. Something to praise and be praised for. So naturally mid-level devs are using them a lot.

  4. And lastly, in such pro-abstraction society, it is hard to learn it might become a problem, focus on it, spot the overuse and very hard to speak up in front of your team. In the end, that's the reason why I write about it. :)

AI is trained on human written code. So naturally it learned this pattern. And from my experience repeats it often.


Every abstraction has a cost​

It is not cheap. And it stacks quickly.

The problem is indirection. Code is less collocated. Program flow jumps back and forth. When reading the code, we need to jump between implementation and its usage. Our brain needs to keep a deeper stack of what is where. Therefore it's harder to navigate a codebase. It stacks and creates broader interfaces, names and parameters to remember. And therefore harder to onboard new people who need to learn more.

Each team member pays this cost. Every time they read the code. Every AI agent pays this too. On every request and every context retrieval. And every small abstraction adds to everyone, every day.

Hard to feel it in the text. So say you just want to know what color this delete button is.

<DeleteButton/>
<DangerButton>Delete</DangerButton>
<Button variant="danger" {...props}/>
danger: "btn-danger"
.btn-danger { color: var(--color-danger) }
--color-danger: #e5484d;

Six files to answer one trivial question.

And your AI agent does not like abstraction either. To answer that same trivial question it has to pull all six files into its context. More tokens. Digging one file after each other. Slower. And literally more expensive, on every single run. Worse, the fuller the context gets, the harder it is to retrieve the right thing from it. Same indirection, same cost. The only new thing is that you now get an invoice for it.


Examples when not to abstract​

Note that all examples are against abstraction. And it's on purpose. It's not that I think we should never abstract. Please abstract. It's crucial for anything non-trivial. Just learn how often and where to put the boundary. I believe all readers can easily imagine situations good for abstraction. As we were taught as juniors. Here I present when it is unnecessary.


1. Constant​

const VARIANT = "outline";
if (mobile) {
    <Button variant={VARIANT}>
} else {
    <Button size="lg" variant={VARIANT}>
}
✗DON'T
if (mobile) {
    <Button variant="outline">
} else {
    <Button size="lg" variant="outline">
}
✓DO

Do we need a VARIANT constant here? Does it need a name? If it were something well known like PI or HTTP_UNAUTHORIZED_STATUS, I would be ok with it. But it's just a general prop value here. It is reused two times here. This is not enough to justify the cost. The rule of three says the same. I would even argue that even three would not be enough here. And it does not hide anything complex. Just a simple string. Moreover, we can expect TypeScript will guard the correct enum value in a variant component prop. No real benefit here. Inline it.


2. JSX Element Mapping​

const social = ["fb", "x", "linkedin"]
return (
    <ul>
        {social.map((id) => (
            <Social key={id} id={id}/>
        ))}
    </ul>
)
✗DON'T
return (
    <ul>
        <Social id="fb"/>
        <Social id="x"/>
        <Social id="linkedin"/>
    </ul>
)
✓DO

This one I see often. Many React developers have a tendency to not duplicate JSX elements in a list. Instead they create an array of data and map over it in the template. But the array does not need a name, is used once and does not hide complexity. The Social component does.

JSX is declarative by itself. It's basically a value expression. Instead of defining an array of strings, we can just define an array of JSX elements. It's fair to say, this works only if the array is static. Note the mapping even costs us a key prop, which the inlined version does not need at all.

See how much more readable it becomes without.


3. Factory Function​

function createUser(name, email, age): User {
    return {
        name,
        email,
        age
   } 
}

const user = createUser(name, email, age)
✗DON'T
const user: User = { name, email, age }
✓DO

In this case, I want to focus on complexity and TypeScript. The factory takes three parameters and passes them to the object. Focus on the complexity of calling createUser function and creating the object. It is the same. The name of the shape, three parameters and some parentheses/braces syntax around. The only difference is that the reader is forced to learn the non-standard createUser function.

TypeScript helps us with the name and guarding the structure while using it. So simply inline the object creation. Even if used in many places.

We can generalize the first two examples here. Both the constant and the factory function try to abstract a value expression (not imperative code statements). In typed codebases it's very hard to justify abstraction of a value. Even a complex one. Try to always improve your type system instead (e.g. introduce enums, string literals, discriminated unions) so it guards the usage instead of introducing an indirection.


4. CSS class​

function DeleteAccountBtn() {
    return (
        <Button className="delete-account-btn"/>
    )
}
.delete-account-btn {
    padding-left: 8px;
}
✗DON'T
function DeleteAccountBtn() {
    return (
        <Button className="padding-left-8px"/>
    )
}
✓DO

This is basically what Tailwind does. It allows developers to style elements without any indirection. Any abstraction. Ultimately collocated. And I think it is the main reason why it is so popular.

Just add a utility class to the element. Done. If you need abstraction, abstract. But do not be forced to do it if not needed. Note the DeleteAccountBtn component is an abstraction too, and a good one. It hides the markup and it names the thing well. That boundary makes sense. The CSS class on top of it is the one adding nothing. Does not hide complexity, the component is already named, and the class is used in the component only.

5. Context with Prop Drilling​

function DeleteAccountModal() {
    const { disabled } = useDeleteAccountContext()
    return (
        <DeleteAccountButton disabled={disabled}/>
    )
}
function DeleteAccountButton({ disabled }) {
    return (
        <Button disabled={disabled}/>
    )
}
✗DON'T
function DeleteAccountButton() {
    const { disabled } = useDeleteAccountContext()
    return (
        <Button disabled={disabled}/>
    )
}
✓DO

This example is not about adding a new layer of abstraction but about placing a logic into a wrong abstraction layer. This DeleteAccountButton abstraction can hide some more complexity which is unneccessary exposed.

One of the main reasons why we use context is to avoid prop drilling. But what I see very often during code reviews is hooking into a context from a parent component, instead of child. This way we have both, the context and prop drilling. Basically taking the disadvantage of both patterns.

The rule of thumb here, is to hook into context from the deepest component which is scoped to it. In other words, closest place where the context value is used.

In this example we move hook useDeleteAccountContext from parent DeleteAccountModal to child DeleteAccountButton. But not deeper into general Buttom component. Because it is meant to be reused also in some other places outside of scope of DeleteAccountModal and its context.

If we would leave it in modal, we would force reader (both human and agent) to jump in between two files and track the usage of the extra prop.


6. Translation Layers​

function useAccountType() {
    const status = useAccountStatus()
    return STATUS_TO_TYPE[status]
}

const STATUS_TO_TYPE = {
    "waitingForApproval": "WAITING"
    ...
}
function UserProfile() {
    const type = useAccountType()
    if (type === "WAITING") {
        return <div>...</div>;
    }
}
✗DON'T
function UserProfile() {
    const status = useAccountStatus()
    if (status === "waitingForApproval") {
        return <div>...</div>;
    }
}
✓DO

My last example is translation layers with little or no logic. Just renaming incoming values. It hides no complex logic, the layer below can be reused the same way, and renaming hurts more than helps. I guess the developers sees that their naming makes more sense. But from my experience, it could be a personal opinion. But must importantly its doubles the naming conventions. So instead of remembering one set of names, we must now two. Increasing our mental load.

From my experience the best is to follow the naming from a well-known libraries and extenral systems you use. Like reusing status names from TanStack query (loading/pending/fetching/idle/...) or following your backend REST endpoint names. Event though they are a bit off for your frontend culture. Its easier to consume just one sub-optimal layer of names. Than one great but sometimes still need to dig into the second sub-optimal anyway.


How Much Extra Do You Pay for AI Agents?​

You pay up to 30 % more for over-abstraction for AI agents. How did I get into the number?

I had a hypothesis. But I do not like to publish just my gut feelings. So I started measuring it. Whole experiment can be found on my GitHub repo. Here I will pin just the most important numbers to keep the article digestable.

The idea was simple. Create two applications. One with nicely collocated code, and one over-abstracted. I will call them collocated and abstracted app. Run an agent with some task on both, measure the cost and time, and compare. Spoiler: I spend tens of hours digging into this rabbit hole. :D

So I did. Two feature identical scientific calculators. Vite, React, Tailwind, SPA. Basic and scientific operations, display, history, theming. The over-abstracted one with 12 extra layers of various abstraction.

The task was to change a color of the equal button. The over-abstracted costs 5x more. Both cost and time wise. Imagine paying $5000 instead of $1000. I was shocked. The same time it was hard to believe. I repeated the measurements 10x to be 95% confident that the difference is not just random variation. Then I started digging deeper.

First thing I wondered was, if the cost was caused by a source code size increase, or abstractions layers. I checked the size and it was really bigger. Flat app was 2,000 lines, the over-abstracted is 3,500 lines. So I created two more calculator variants. I took a over-asbtracted one and remove some features, so it lands on rougly 2,000 lines too. And I took a flat calculator and add some more features into it, so it landed rougly 3,500 lines.

I run the task again againts all four apps. This time I saw just 3x increase. I also measured number of AI model turn arounds. Usually needed when AI decides to read a file, analyze it and then decide again what to do next. There is measurable 2.2x times increase in number of rounds. So I was confident the reasons are really a abstraction layers. But the 3x increase was still hardly believable I was not confident to quote it in my article. I started digging deepr and analyzing what costs some much.

I started playing with task prompts. Changing the color is chosen to hit the abstractions hard. So I designed 7 different tasks for AI. Including an adding new feature, removing feature, refactor a code, fix a bug. One of the task was designed to hit the flat app hard. Change the values inside single over-abstracted layer. But changing 12 files in a flat variant.

TaskWhyCostTime
Change one value at one leaffinding the place; all apps edit one file5.0x4.3x
Send a value through the view modelcrossing layer boundaries2.1x2.3x
Edit one stringminimal possible task, one line in all apps1.8x1.6x
Delete a featureunpicking vs deleting1.6x1.3x
Add a new operation keygrowing a registry vs adding a leaf1.3x0.9x
Find and repair a defectfinding, rather than specifying0.9x1.3x
Restyle twelve keys at oncethe case abstraction is built for0.8x0.7x

The cost varies between 5x - 0.8x. There are tasks on which the over-abstracted app is both cheaper and faster. However its good to mention, that for the last task i had to disable bash tooling for the AI agent. Otherwise it uses bash sed for updating 12 files in a collocated app and was again 1.3x cheaper.

So the final number depends on what you do with your codebase. But still I wanted something to quote. I asked Fable 5 to gather all the information from the experiment and try to extrapolate the numbers for a real mid-large codebase under a regular development. It answered 40 % with a model how it got there.

For me, the number feels still unexpected and huge. And hard to quote. I would love to continue digging one more level deep. But now I will go to sleep and spend some time with my family. After all those hours of playing with it, Im confident enough to quote this:

Over-abstraction has a price: an estimated 30 % increase in your AI agent costs, extrapolated from 394 agent runs on four modeled codebases.


Conclusion​

Abstractions can have benefits, and our codebase cannot live without them. But ...

Every abstraction has a cost. In both human mental load and AI agent bill. We often pay the cost without getting any real benefit.

Every created indirection stacks. Introduced by you, your colleagues, your AI agents. Those indirection costs are paid by you, your colleagues, your agents, every time the codebase is read, every day.

After experiment with 394 agent runs on four codebases I can confidently estimate, that development on over-abstracted codebase costs 30 % more in AI agent bill and time than a development on a collocated one.

Think before you abstract. Look for overusing it during code reviews. Tell your team. Instruct your agents.

Thank you for reading.
