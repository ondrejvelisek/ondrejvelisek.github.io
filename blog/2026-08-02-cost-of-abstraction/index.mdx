# Cost of Abstraction

Over my career I saw many <abbr title="mid-level">medior</abbr> developers craving more and more abstraction. 
I was one of them. But over time I see that more is not always better.
A truly senior dev abstracts only when it is needed.
And I believe it is less than most developers think.
And therefore AI overuses abstraction too.


{/* truncate */}

This is not a new idea but a well-known topic.
I got inspired by Dan Abramov's
[The WET Codebase](https://overreacted.io/the-wet-codebase/).
Sandi Metz in the post [The Wrong Abstraction](https://sandimetz.com/blog/2016/1/20/the-wrong-abstraction)
put it even shorter: "duplication is far cheaper than the wrong abstraction".
I want to add my own frontend dev view, my experience with TypeScript and AI, and examples I saw over time.



<br />



## What is abstraction?

It is a boundary between two parts of code: the code it hides, and the code that uses it via an interface.
This interface has a name, is reusable, and can have some parameters. The best example is a function.

```typescript noBottomMargin
function sort(array: Array<number>) {
    // implementation code it hides behind the interface
}
```
```typescript
// some higher level code uses the interface
sort([2, 1, 3]);
```

But there are some other forms of abstraction which may not be that obvious.

- variable/constant
- JS class
- CSS class
- component
- file
- package
- repository
- programming language

Try to think about how the boundary is represented in each of those.
What its interface looks like. What its name is. What it hides and how to reuse it.



<br/>



## Why abstract?

Abstractions are crucial for code maintainability. And it's the reason why we are capable of building large systems.
Imagine you had to always write code for sorting an array or multiplication of two numbers. Nightmare.

So we abstract to:

- Hide complexity
- Name a piece of code
- Reuse a piece of code

If none of the above is needed, we should not abstract. And even though some of the above applies,
we still should consider not to. We need to balance the cost with the benefit.

The question I asked myself is why developers overuse them so often. I see three reasons.

1. It is a very quiet enemy. It walks in the shadows. And it adds up slowly.
One wrong abstraction does almost nothing to us and our velocity.
So it's hard to focus on and spot it. I believe the main reason is somewhere else. 

1. Every junior developer, including me, when starting to code, naturally did not create abstractions much.
We focused on the goal. To make it work. It was hard enough for us. Challenging on its own.
And we did not have the capacity or time to think about something like abstractions.
Junior devs tend to create long functions and files, duplicate code, and do not name the interfaces nicely.
And their senior mentors tell them to split the code. Reuse lines. Name the functions better.
Hide the complexity behind interfaces, ... Abstract more. It is taught in courses and university lectures.
DRY, SOLID, Single responsibility, KISS, one page function, High Cohesion & Low Coupling, Separation of Concerns, ... 
All those principles are very well known. Because everybody was a junior once.
It almost becomes a SW dev culture. Abstractions are perceived as a good code practice. Something to praise and be praised for.
So naturally <abbr title="mid-level">medior</abbr> devs are using them a lot.

1. And lastly, in such pro-abstraction society, it is hard to
learn it might become a problem, focus on it, spot the overuse and very hard to speak up in front of your team.
In the end, that's the reason why I write about it. :) 

AI naturally learned this pattern from humans. And from my experience repeats it often.



<br/>



## Every abstraction has a cost

It is not cheap. And it stacks quickly.

The problem is indirection. Code is less collocated. Program flow jumps back and forth.
When reading the code, we need to jump between implementation and its usage.
Our brain needs to keep a deeper stack of what is where.
Therefore it's harder to navigate a codebase.
It stacks and creates broader interfaces, names and parameters to remember.
And therefore harder to onboard new people who need to learn more.

Each team member pays this cost. Every time they read the code.
Every AI agent pays this too. On every request and every context retrieval.
And every small abstraction adds to everyone, every day.

Hard to feel it in the text. So say you just want to know what color this delete button is.

```tsx noBottomMargin
<DeleteButton/>
```
```tsx noBottomMargin
<Button variant="danger">Delete</Button>
```
```typescript noBottomMargin
danger: "btn-danger"
```
```css noBottomMargin
.btn-danger { color: var(--color-danger) }
```
```css
--color-danger: #e5484d;
```

Five files to answer one trivial question.

And your AI agent is no different. It does not like abstraction either.
To answer that same trivial question it has to pull all five files into its context.
More tokens. Slower. And literally more expensive, on every single run.
Worse, the fuller the context gets, the harder it is to retrieve the right thing from it and the easier it is to get lost jumping around.
Same indirection, same cost. The only new thing is that you now get an invoice for it.

## Examples when not to abstract

Note that all examples are against abstraction. And it's on purpose.
It's not that I think we should never abstract. Please abstract. It's crucial for anything non-trivial.
Just learn how often and where to put the boundary.
I believe all readers can easily imagine situations good for abstraction.
As we were taught as juniors. Here I present when it is unnecessary.



<br/>



### 1. Constant 

```typescript dont
const VARIANT = "outline";
if (mobile) {
    <Button variant={VARIANT}>
} else {
    <Button size="lg" variant={VARIANT}>
}
```

```typescript do
if (mobile) {
    <Button variant="outline">
} else {
    <Button size="lg" variant="outline">
}
```

Do we need a `VARIANT` constant here?
Does it need a name? If it were something well known like `PI` or `HTTP_UNAUTHORIZED_STATUS`, I would be ok with it. But it's just a general prop value here.
It is reused two times here. This is not enough to justify the cost.
The [rule of three](https://en.wikipedia.org/wiki/Rule_of_three_(computer_programming)) says the same. I would even argue that even three would not be enough here.
And it does not hide anything complex. Just a simple string.
Moreover, we can expect TypeScript will guard the correct enum value in a `variant` component prop. 
No real benefit here. Inline it.




<br/>



### 2. Factory function

```typescript dont
function createUser(name, email, age): User {
    return {
        name,
        email,
        age
   } 
}

const user = createUser(name, email, age)
```

```typescript do
const user: User = { name, email, age }
```

In this case, I want to focus on complexity and TypeScript.
The factory takes three parameters and passes them to the object.
Focus on the complexity of calling `createUser` function and creating the object. It is the same.
The name of the shape, three parameters and some parentheses/braces syntax around.
The only difference is that the reader is forced to learn the non-standard `createUser` function.

TypeScript helps us with the name and guarding the structure while using it.
So simply inline the object creation. Even if used in many places.

We can generalize the first two examples here.
Both the constant and the factory function try to abstract a value expression (not imperative code statements).
In typed codebases it's very hard to justify abstraction of a value. Even a complex one.
Try to always improve your type system instead (e.g. introduce enums, string literals, discriminated unions)
so it guards the usage instead of introducing an indirection.




<br/>



### 3. JSX Element mapping

```tsx dont
const social = ["fb", "x", "linkedin"]
return (
    <ul>
        {social.map((id) => (
            <Social key={id} id={id}/>
        ))}
    </ul>
)
```

```tsx do
return (
    <ul>
        <Social id="fb"/>
        <Social id="x"/>
        <Social id="linkedin"/>
    </ul>
)
```

This one I see often. Many React developers have a tendency to not duplicate JSX elements in a list.
Instead they create an array of data and map over it in the template.
But the array does not need a name, is used once and does not hide complexity. The Social component does.

JSX is declarative by itself. It's basically a value expression.
Instead of defining an array of strings, we can just define an array of JSX elements.
It's fair to say, this works only if the array is static.
Note the mapping even costs us a `key` prop, which the inlined version does not need at all.

See how much more readable it becomes without.




<br/>



### 4. CSS class

```tsx noBottomMargin
function DeleteAccountBtn() {
    return (
        <Button className="delete-account-btn"/>
    )
}
```
```css dont
.delete-account-btn {
    padding-left: 8px;
}
```

```tsx do
function DeleteAccountBtn() {
    return (
        <Button className="padding-left-8px"/>
    )
}
```

This is basically what Tailwind does. 
It allows developers to style elements without any indirection. Any abstraction. Ultimately collocated.
And I think it is the main reason why it is so popular.

Just add a utility class to the element. Done. If you need abstraction, abstract. But do not be forced to do it if not needed.
Note the `DeleteAccountBtn` component is an abstraction too, and a good one.
It hides the markup and it names the thing well. That boundary makes sense.
The CSS class on top of it is the one adding nothing. 
Does not hide complexity, the component is already named, and the class is used in the component only.



<br/>



## Conclusion

Abstractions can have benefits, and our codebase cannot live without them. But ...

Every abstraction has a cost.
We often pay the cost without getting any real benefit.

Every created indirection stacks. Introduced by you, your colleagues, your AI agents.
Those indirection costs are paid by you, your colleagues, your agent swarms, every time the codebase is read, every day.

Think before you abstract. Look for overusing it during code reviews. Tell your team. Instruct your agents.

Thank you for reading.
