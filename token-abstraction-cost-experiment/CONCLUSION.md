# What abstraction costs an AI agent

I built the same calculator twice. One version is flat: every key is a file that owns
everything about itself. The other is layered: twelve levels of indirection, all of them
patterns that look disciplined in a code review. Same 61 buttons, same behaviour, same tests.

Then I asked an agent to change each of them, and measured what it spent.

I got a number. Then I ran a second task and got a very different one. By the seventh task the
honest answer had stopped being a number and had become a shape.

## There is no single number

Across six kinds of change, the layered app costs anywhere from **0.84× to 4.97×** what the flat
app costs. The direction depends entirely on what you ask for. Four groups:

**Saying what to change is extremly more expensive for abstracted app.** Change one key's colour: 4.97×. Move a stored value into
the display: 2.07×. The colour change is the largest and most reliable effect in the experiment;
the display one is borderline at p=0.052.

**Growing or shrinking a feature is moderately expensive.** Removing a feature costs 1.61x.
Adding one costs 1.25x to 1.59x, and takes about 1.5x the turns. The two size-matched
comparisons are clear (p=0.015 and p<0.001); the same-features pair is not (p=0.089). `add` is
the noisiest task in the suite, because how thoroughly the agent implements a new key varies a
lot from run to run, so it needed more runs than anything else to separate at all.

**Finding a defect is more or less the same.** Given a bug report in plain user language, with no
word that appears in the source, both shapes take exactly the same number of turns. The layered
app comes out 12–15% cheaper and 29–72% slower, depending on which pair you compare.

**Changing many places at once favours the layered abstraction app.** Recolouring twelve keys is one edit
there and twelve in the flat app: 16–23% cheaper on all three comparisons, and up to a third
faster on two of them. The small pair shows almost no time difference, so treat the speed-up as
the weaker half of that claim.

The per-task numbers, with confidence intervals, are in [RESULTS.md](RESULTS.md).

### Which number to quote

Those figures come from comparing the two apps that have **identical features**. That pair is
honest about behaviour but not about size: the layered app is also 1.69 times the tokens, so its
ratio contains both effects at once.

The other two comparisons hold size still instead, and they agree with each other:

| Leaf colour change | ratio |
| --- | --- |
| Same features, layered tree also bigger | 4.97× |
| Same size, big apps | 2.99× |
| Same size, small apps | 2.92× |

**So the price of structure alone is about 3×, and about 5× once the extra code that structure
brings with it is included.** Quote 3× when you mean shape. Quote 5× when you mean "what it
actually cost me to own the layered version", because in real life you do not get to keep the
smaller tree.

Every conclusion below holds on all three comparisons. Nothing changes sign between them.

## Why: the agent pays by the turn

The bill is not made of code. Across 314 runs, the number of round trips to the model predicts
cost almost perfectly (r = 0.90). The size of the source tree predicts nothing at all
(r = 0.00). A turn costs about a penny and about three and a half seconds, whatever app it
happens in.

So the question is never "how much code is there". It is "how many times does the agent have to
stop and look again".

Size is not entirely free. On the one task that is pure searching, a tree 1.6 times bigger cost
about 1.7 times more — in **both** shapes equally. But on most tasks growing the tree changed
nothing measurable, and `collocated-big` — the largest app here, carrying fifteen converters
nobody ever asks about — stays among the cheapest. Code the agent never walks through is close
to free.

Depth is the axis that hurts. Every layer boundary is one more place where the agent has to
stop, read, and work out where to go next. That is a turn, and turns are the bill.

With one refinement, which `add` exposed: not every turn costs the same. A turn that only replays
context the model has already seen is cheap — replayed tokens bill at about a twentieth of new
ones, and a fortieth of output.
The expensive turns are the ones that open a file for the first time. That is why adding a feature
can take 60% more turns and still land inside the noise on price, while changing one colour, where
almost every extra turn opens something new, costs five times as much.

## The obvious objection, tested

The flat app has a file called `EqualsButton.tsx`. The task said "change the = key accent
colour". So of course the flat app wins: the request contains the file name.

That objection is good enough that it needed its own experiment. I asked for the identical
change again, in words that match no file name and no token name anywhere in either app:

> the key that finishes a calculation and shows the answer should be purple instead of the
> colour it is now

Rewording closed about 15% of the gap and left the rest standing, with a confidence interval
that stays far above 1. Name matching is real, and it is small. The rest is structure.

### Better context helps, but does not close the gap

Naming the target file paths in the prompt — the `located` control — is the answer to the obvious
objection: just tell the agent where to look.

Measured against `local` and `ripple` under the **same** prompt condition and the same number of
runs, naming the files moves the layered penalty from 2.02× to 1.79×, with confidence intervals
that overlap almost completely. The gap does not close.

It does make both apps cheaper. Handing over the paths, and asking for both changes in one
session instead of two, saves 36% and 45% on the two layered apps and 32% and 53% on the two flat
ones. Similar sizes, no consistent direction. Better context is worth having, and it is not a
cure for shape.

One trap worth naming, because I fell into it while writing this up. The `located` figures come
from the self-check condition, where the agent is also told to typecheck and fix its own errors.
That instruction adds a similar fixed amount of work to every app, which pulls every ratio toward
1. Comparing a self-check number against a baseline number therefore invents an improvement that
is not there — `local` reads 4.97× at baseline and 2.02× under self-check, on the same code and
the same request. Only compare within a condition.

## What the layered app buys

Two things, and both showed up in the measurements rather than in an argument.

**A second index.** Concern-named directories work like a table of contents. A bug report names
a concern, and `engine/handlers/entry.handlers.ts` is right there in the tree listing. Layered
runs typically read one small, precisely-named file. Flat runs open the big shared context file
instead, which pulls more new text into the conversation, and new text is billed about twenty
times more than text the model has already seen. That is the whole reason the layered app is
cheaper at diagnosis.

**One place to change instead of twelve.** When a change genuinely is cross-cutting, the layered
app edits one file and takes fewer than half as many turns.

Neither of these is a surprise to anyone who has worked in a well-factored codebase. What is new
is that they now have a price attached, and so does the cost on the other side.

## What I would not conclude

- **Not "abstraction is always bad".** It is cheaper on two of the seven tasks, more expensive on 2 tasks,
  and dramatically more expensive on three.
- **Not that the magnitudes transfer.** These apps are 2,000 to 3,600 lines. At that size
  everything is two hops from everything else, which is exactly why navigating by directory name
  works so well. In a much larger codebase the layered app's advantage at finding things will
  grow, but its penalty for editing will grow too.
- **Not that twelve layers is normal.** It is a caricature, chosen to make the effect big enough
  to measure. Real codebase sits somewhere between, and would show a smaller effect in both directions.

## One number anyway

The benchmark refuses to give a single number, and it is right to. But a reader who has to make
a decision wants one. So I asked for a guess instead of a measurement.

I had Claude Fable 5 read the whole repository — every payload, every table, every run log, the
design, the caveats — and gave it this prompt:

> From everything you know — all the experiments, findings and comparisons — distil one number.
> Compare the layered and the collocated codebase styles. Think of a real, medium-to-large
> codebase under a normal development cycle: some bugs, some new features, a few removals, some
> refactoring. Regular developer prompts. What is your guess? Answer with a single number.

It answered **1.4×**: an over-abstracted codebase costs roughly 40% more in agent tokens and time
than a collocated one, over a normal cycle of work.

How it got there. It weighted the measured ratios by a plausible task mix — about 40% small
targeted changes, 25% feature additions, 20% bug fixes, 10% cross-cutting refactors, 5% removals
— which lands at 1.6–1.8× on this suite's numbers. Then two corrections pulled the figure down.
Both apps here are caricatures: real layered code has three or four hops where these have four to
six, and the penalty scales with hops. And the size-matched comparisons show pure structure costs
about 3× on the worst task, not 5×; the 5× includes code volume a real project would carry
anyway. Two things pushed it back up: real codebases are 50–100× larger, so the naming shortcut
that rescues the layered app here gets less reliable while the edit fan-out does not shrink; and
real prompts are vaguer than these, which taxes whichever shape needs more navigation.

It put the honest range at 1.15× to 1.8×. Below that, the layered app's advantages at diagnosis
and cross-cutting change would have to dominate a normal week, and they do not. Above it, real
layering would have to be as extreme as this experiment's, and it is not.

**This is a guess, not a measurement.** It is a guess informed by 394 verified runs on toy
codebases, made by a model reading its own kind's bills. The benchmark itself cannot say it, and
nothing in [RESULTS.md](RESULTS.md) supports it directly. Take it as a considered opinion with
the reasoning shown, and nothing more.
